# Контекст разработки (для Copilot)

История ключевых решений из сессии проектирования. Читать перед работой над архитектурой.

## Что за проект

HyperVOrchestrator — персональный инструмент для массового поднятия Windows-VM за NAT'ом.
Полный цикл: сборка VHDX из ISO с unattend → создание VM → дебладинг гостя → сеть → .NET + Office → cleanup.
Пользователь — сам автор, полуручной режим через консольный TUI.

Питон-сервер на хосте — центральная сетевая точка: HTTP-прокси для гостей + TCP-форвардинг (RDP наружу).
Цель: несколько VM за одним NAT, каждая со своим форвард-портом и прокси.

## Главное архитектурное решение

Граница C# / PowerShell проводится **по наличию ветвления**, не по технологии:

- **Линейные фазы остаются PowerShell-скриптами** с check-механизмом (exit 0 = выполнять main, exit 2 = уже сделано):
  - `scripts/SetupVM/` — установка и настройка Windows (бывшие 00-CreateAndWinInstall + 10-GuestSetup)
  - `scripts/InstallSoft/` — dotnet, office, cleanup (бывшие 40/50/60)
- **Сетевая настройка — чистый C#** (`NetworkSetup` + экзекьюторы), потому что там комбинаторное состояние
  (NAT есть/нет, IP статический/динамический, прокси жив/мёртв, форварды). Скрипты только исполняют
  атомарные задачи (`scripts/_system/{ExecutorName}/*.ps1`, JSON на выходе → FSModels).
- Паттерн экзекьюторов НЕ расползается на линейные фазы — это было бы копипастой.

## Верхний уровень

Три больших метода + «запустить всё»:
1. **SetupVM** — прогон скриптовых сьютов из `scripts/SetupVM`
2. **ConfigureNetwork** — C#-степы из `NetworkSetup.GetSteps(vm)`, каждый запускаем отдельно
3. **InstallSoft** — прогон `scripts/InstallSoft`
4. **Full Setup** — всё подряд, останов на первом фейле

Навигация в TUI: выбор хоста → `Initializer.LoadHost()` → список VM → `LoadVmInfo(host, vm)` →
меню действий (1-4 + Back). Вложенные while-циклы в `Orchestrator`, никакого стека экранов.
`ConsoleModelViewer`: `ShowMenu` (плоское меню) + `ShowTree` (дерево скриптовых степов).
Весь вывод только через viewer — потом возможна замена на WinForms заменой одного класса.

## Правила работы (требования пользователя)

- **Никакого overkill**: не создавать интерфейсы/абстракции «на вырост», не закрывать все возможные
  случаи. Выделять конечные состояния, делать минимально достаточное. Action'ы вместо IStep и т.п.
- **Строго держаться поставленной задачи**: никаких побочных предложений, «а ещё можно сделать»,
  попыток решить всё сразу. Это мешает, а не помогает.

## Технические заметки

- PSSession: одна персистентная сессия на таргет (`New-PSSession -VMName -Credential` один раз,
  дальше `Invoke-Command -Session $s` без кредов и реконнекта, ~1-3 сек экономии на вызов,
  состояние runspace сохраняется). Сессия умирает при ребуте VM — нужен reconnect. Ещё не реализовано.
- Заглушки `//script` в NetExecutor/PythonExecutor (CreateNatNet, SetStaticIp, GetFreePort, SetProxy,
  EnableRdp, Start, StartProxy, StartForward...) — следующая задача.
- `Host.GlobalNetInterface` нигде не заполняется — NRE на шаге форвардинга, починить при реализации сети.
- `scripts/VM/20-HostNetwork` и `30-GuestNetwork` — легаси, умрут когда C#-сеть заработает.
- Выделение свободного IP: не перебор IsIpFree по одному, а один скрипт GetUsedIps + выбор в C#.
- Передача параметров в executor-скрипты: механизма пока нет (только ExecutorTarget через StateKeeper),
  понадобится для SetStaticIp(ip) и т.п.
- Интерполяция `{state.vm.*}` работает через `StateKeeper.CurrentVm` (ставится в LoadVmInfo).
  `{vm.name}` берётся из конфига — учитывать при запуске на VM, выбранной не из конфига.
