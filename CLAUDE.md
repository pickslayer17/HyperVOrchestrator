# TestRunner — VM provisioning project

> Этот файл — точка входа в контекст для Claude Code. Прочитай целиком прежде чем что-либо делать или предлагать.

---

## 1. Что это и зачем

Проект автоматизирует развёртывание Windows 11 ВМ на Hyper-V под автотесты FlaUI (UI Automation на .NET). Параллельно поднимается **2-4 ВМ** на одном хосте. Цель — воспроизводимая, безглючная процедура установки и конфигурации тестовой машины с нуля.

Пользователь — программист со стажем (разные языки). Sysadmin/DevOps задачами занимается впервые **профессионально**, поэтому хочет, чтобы было **по-программистски структурно**, а не "куча скриптов в папке". Бытовой хаос сисадминской культуры его раздражает — это ВАЖНО для тона предложений.

## 3. Стек и языковые решения

| Слой | Язык | Статус |
|---|---|---|
| Оркестратор (CLI, меню, запуск шагов) | **C#** | желаемое — при условии что соберётся self-contained без необходимости ставить .NET runtime |
| Гостевые "рецепты" (что делать внутри ВМ или на хосте) | **PowerShell** | остаётся |
| Прокси (`Hyper-V Proxy.py`, `RDP_forward.py`) | **Python** | остаётся **как есть** на ближайшее время. Только IP/порты вынести в конфиг. C#-переписывание сейчас не делаем. |

### Открытый вопрос про C#
Пользователь хочет, чтобы **бинарь оркестратора запускался "из коробки"** на хосте без установленного .NET. Это решается через **self-contained single-file publish** (`dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true`) или **NativeAOT** (`-p:PublishAot=true`).

Перед началом работы над оркестратором: **проверить, что self-contained сборка реально работает чисто** на хосте без dotnet, в т.ч. с `System.Management.Automation` (PowerShell SDK) внутри. AOT с PS SDK исторически плохо дружил — проверить актуальное состояние. Если AOT не идёт — self-contained single-file (получится ~70-100 MB exe, это норм) подойдёт.

Если по итогу проверки C# self-contained по какой-то причине не годится — **fallback на PowerShell для оркестратора тоже**. Но C# предпочтительнее.

## 4. Архитектура оркестратора

### Запуск
- `run.cmd` (или как назовём) в корне репо — тонкая обёртка над exe.
- **Всегда** запрашивает повышение прав (UAC) — главное окно консоли работает под админом.
- Находит корень проекта через `AppContext.BaseDirectory` / расположение exe. Все пути — относительные от корня. **Никаких `D:\VMs` в коде или конфиге.**

### UI
Простая нумерованная меню-консоль. Пример:

```
  TestRunner orchestrator
  =======================

  [✓] 1. Enable Hyper-V on host          (зелёный)
  [✗] 2. Setup host network (NAT)        (красный)
  [ ] 3. Create VM                       (светло-сине-фиолетовый, не запускался)
  [ ] 4. Install Windows
  ...

  Choose step:
```

Пользователь вводит цифру, жмёт Enter, оркестратор выполняет шаг. По окончании — снова меню с обновлёнными статусами.

### Цвета (обязательно)
- **Светло-сине-фиолетовый** — пункт, который ещё не запускался / нейтральное состояние.
- **Зелёный + `[✓]`** — шаг успешно выполнен / уже сделан.
- **Красный + `[✗]`** — шаг упал / не выполнен / нельзя выполнить.

Используй `Spectre.Console` (NuGet) — он умеет цвета, чекмарки, прогресс. Если решим без зависимостей — `Console.ForegroundColor`.

### Контракт шага (Step)

Каждый шаг меню — это класс, реализующий интерфейс. Контракт **строгий**:

```csharp
interface IStep
{
    string Name { get; }            // "Create VM"
    string Description { get; }      // короткое описание для меню

    // Можно ли сейчас вообще пытаться выполнить шаг?
    // (например: для "create VM" нужен включённый Hyper-V и наличие ISO)
    StepCheckResult CanDo();

    // Не сделано ли уже то, что мы хотим?
    // (для "create VM": существует ли уже ВМ с таким именем)
    StepCheckResult IsAlreadyDone();

    // Собственно выполнение
    StepResult Do();
}
```

Каждый из трёх методов под капотом вызывает свой PowerShell-скрипт. Логика всего шага:
1. `CanDo()` → если false, показать причину, не выполнять.
2. `IsAlreadyDone()` → если true, пометить ✓ и выйти.
3. `Do()` → выполнить, результат → ✓ или ✗.

Это даёт **идемпотентность из коробки**: запустил шаг 10 раз — он 9 раз скажет "уже сделано", один раз сделает.

### Запуск скриптов
Два режима, оба обёрнуты в методы оркестратора:

1. **Host-side** — скрипт исполняется на хосте локально под админом. Просто открыть `Runspace`, выполнить.
2. **VM-side** — скрипт исполняется внутри ВМ через `Invoke-Command -VMName ... -Credential ...`. Метод-обёртка получает имя ВМ + ScriptBlock, креды берёт из конфига сам. **SSH не используем**. Только PSDirect/WinRM с кредами.

Сигнатуры будут примерно такие:
```csharp
ScriptResult RunOnHost(string scriptPath, IDictionary<string,object>? args = null);
ScriptResult RunInVm(string vmName, string scriptPath, IDictionary<string,object>? args = null);
```

### Remote execution
**Сейчас НЕ делаем.** Оркестратор запускается на самом Hyper-V хосте. Но архитектуру держать такой, чтобы добавить `--host <name>` флаг было простым делом (т.е. `RunOnHost` в будущем может уходить в remote runspace, а не локальный).

### Принципы структуры
- **positive/ и negative/ зеркальны по именам файлов**: если в positive есть `20-vm/New-Vm.ps1`, в negative должен быть `20-vm/New-Vm.ps1`, проверяющий "не создана ли уже эта ВМ".
- **Префиксы цифрами** (`10-`, `20-`…) задают логический порядок этапов, не строгий порядок выполнения.
- **Скрипты — чистые функции**: на вход `param([hashtable]$Config)` или конкретные параметры, ничего не знают про корень проекта, ни про другие скрипты, не дотсорсят соседей. Все нужные значения приходят параметрами от оркестратора.
- **Сейчас существующие папки** (`setup_network/`, `setup_office/`, `after_setup/`, `before_setup/`, `setup_access/`, `setup_dotnet/`, `unattend/`) после миграции **удалить**.

## 6. Конфиг

Два файла, оба JSON:

**`config/default.config.json`** — в git, со структурой и dummy-значениями:
```json
{
  "vm": { "name": "TestRunner", "memoryGb": 4, "cpuCount": 4, "diskSizeGb": 40 },
  "credentials": { "user": "", "password": "" },
  "network": {
    "switchName": "NATSwitch",
    "hostIp": "192.168.50.1",
    "vmIp": "192.168.50.2",
    "prefix": 24,
    "proxyPort": 3128,
    "rdpForwardPort": 13389,
    "dnsServer": "8.8.8.8"
  },
  "paths": {
    "windowsIso": "",
    "officeArchive": ""
  },
  "office": { "channel": "Current", "edition": "64", "apps": ["Word"] }
}
```

**`config/local.config.json`** — в .gitignore, реальные значения. Мерджится поверх default.

Загрузка через `Microsoft.Extensions.Configuration` (`AddJsonFile(default)` + `AddJsonFile(local, optional:true)`). Дальше pojo-биндинг в типизированный `AppConfig` объект, который раздаётся шагам.

В PowerShell-скрипты конфиг прокидывать как `[hashtable]` через `AddParameter("Config", configHashtable)`.

- `TestRunner`, `TestUser`, `Test1234!`
- `192.168.50.1`, `192.168.50.2`, `3128`, `13389`, `8.8.8.8`
- `NATSwitch`
- `C:\Users\TestUser\Desktop\...`
- Путь к ISO, к office.zip
- Список Office apps

### Phase 3 — Собрать конфиг
Сложить `config/default.config.json` (с пустыми кредами и пустыми путями к артефактам) и `config/local.config.json` (с реальными). Зафиксировать в .gitignore.

### Phase 4 — Разнести скрипты по `positive/`
Перенести каждый существующий скрипт в `positive/NN-area/Verb-Noun.ps1`. **Параметризовать** — убрать хардкод, на вход `[hashtable]$Config` или явные параметры. Каждый скрипт самостоятелен.

### Phase 5 — Написать `negative/` зеркала
Для каждого `positive/.../X.ps1` написать `negative/.../X.ps1` с проверкой "не сделано ли уже". Должен возвращать булево (через exit code или output) — есть/нет.

Примеры проверок:
- ВМ создана? → `Get-VM -Name ... -ErrorAction SilentlyContinue`
- NATSwitch есть? → `Get-VMSwitch -Name ...`
- .NET SDK стоит? → `Test-Path "C:\Program Files\dotnet\dotnet.exe"` внутри ВМ
- Office установлен? → реестр HKLM\SOFTWARE\Microsoft\Office\...

### Phase 6 — C# оркестратор
В `core/` поднять .NET console project (.NET 8 или 10 — решим в момент). Реализовать:
- Конфиг-лоадер
- `RunOnHost` / `RunInVm` обёртки (PowerShell SDK)
- `IStep` интерфейс
- Меню (Spectre.Console или ручной)
- Манифест шагов (порядок, имена, маппинг на скрипты в positive/negative)

Каждый Step — короткий класс, который знает только пути к своим двум скриптам и логику отображения.

### Phase 7 — `run.cmd`
Тонкая обёртка с self-elevation (PowerShell `Start-Process -Verb RunAs` или нативный manifest на exe). Запускает `core/bin/.../Orchestrator.exe`.

### Phase 8 — Удалить старое
Когда всё мигрировано и проверено вручную — удалить старые папки (`setup_*`, `before_setup`, `after_setup`, `unattend`, `to_do.txt`, корневые `start_vm.ps1`, `connect_vm.ps1`, `flaui.ps1` — заменяются пунктами меню или утилитарными шагами).

Каждая фаза = отдельный коммит. Возможность откатить любую.

## 8. Что НЕ делать (важно)

- **Не делать async**. Шаги выполняются последовательно, синхронно. Параллелизм рассматриваем точечно, когда конкретная задача его потребует.
- **Не тащить SQLite / БД** для state. Если нужно хранить "что выполнено" — простой JSON в `artifacts/state.json` или вообще никак (полагаться на `IsAlreadyDone` каждый раз).
- **Не писать тесты** (xUnit и т.п.). Это рабочий тулинг для одного человека, тесты сейчас — overengineering.
- **Не переписывать Python-прокси на C#** сейчас. Только параметризовать IP/порты.
- **Не делать SSH-вариант** удалённого выполнения. Только WinRM/PSDirect + креды.
- **Не делать `--host <remote>`** прямо сейчас, но писать `RunOnHost` так, чтобы это добавлялось одной точкой расширения.
- **Не вводить DI-контейнер** (Microsoft.Extensions.DependencyInjection и т.п.) ради DI. Простой `new()` достаточно. Если естественно само сложится через `IHostBuilder` ради конфига/логгера — ок.
- **Не вводить структурный логгер** (Serilog и пр.). `Console.WriteLine` с цветами достаточно.
- **Не предлагать Packer / Ansible / Terraform.** Решение принято: PowerShell + C# + Python. Альтернативы не обсуждаем.
- **Не использовать абсолютные пути** в коде/конфиге/скриптах. Никаких `D:\VMs`. Корень — от расположения exe.

## 9. Стиль общения

Пользователь активно даст знать, если что-то не так. Несколько правил, которые он уже обозначил явно:

- **Конкретика, а не вода.** Списки "что у тебя плохо организовано" и обобщения "сисадминство — это хаос" — раздражают. Если что-то предлагаешь — предлагай **минимально необходимое**, не разворачивай 7 разделов из учебника.
- **Не overthink.** Если задача "сделай гит-инит" — не превращай в эссе про IaC-индустрию.
- **Не повторять то, что уже решено.** Решения зафиксированы в этом файле (раздел 8 в т.ч.). Не возвращайся к ним без явной просьбы.
- **Опираться на анализ реального кода**, не на абстракции. Если предлагаешь рефакторинг — ссылайся на конкретные файлы и строки.
- **Русский язык — основной** в общении. Скрипты/код — английский (имена, комментарии — как принято для конкретного языка).
- **Не льстить, не извиняться без необходимости.** Если облажался — признай в одну строку и иди дальше.
